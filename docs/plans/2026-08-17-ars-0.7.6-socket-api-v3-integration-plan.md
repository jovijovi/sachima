# Sachima × agent-run-supervisor 0.7.6 — arsd Socket API v3 Implementation Plan

> **Type:** Implementation plan (candidate). Docs-only until separately approved.
> **Status:** 0.7.6 calibration candidate — **acceptance pending**. It calibrates the accepted 0.7.1 plan to released ARS 0.7.6. While acceptance is pending, the **accepted 0.7.1 Spec/plan pair remains the active governing integration authority**; this document is candidate authority only and supersedes nothing yet.
> **Governing Spec:** `docs/plans/2026-08-17-ars-0.7.6-socket-api-v3-integration-spec.md` (calibration candidate, acceptance pending — governing **on acceptance**; the accepted 0.7.1 Spec governs until then).

## 1. Goal

Migrate Sachima from the removed `agent-run-supervisor` **library** backend to an operator-managed **`arsd` 0.7.6 daemon over Socket API v3 / Native ACP**, default-off and fully offline-testable, without a silent fallback and without fabricating terminal truth.

The deliverable is a usable integration: one admitted Sachima turn becomes exactly one durable ARS Run under a Sachima-derived idempotent `request_id`; Sachima privately and **durably** binds that dispatch to `(run_id, ars_session_id)` so observation resumes after a restart without re-dispatching; later turns reuse the same durable ARS Session; and user-visible status moves only on trusted Run terminal evidence.

Nothing in this plan turns `arsd` on, runs a real AGENT, or touches Gateway runtime, delivery, or production. `fake` stays the default and stays green.

## 2. Architecture

Five layers, each with one owner. The migration changes the two middle layers and leaves the outer two intact.

```text
Sachima canonical spine        TaskRegistry / TaskEventLog (single seq authority)
                               Status Projection: created|running|permission_wait|
                                                  completed|failed|cancelled
        ▲ (canonical status only; never a raw id, never a foreign cursor)
        │
Runtime Spine port layer       AgentRunSupervisorPort / ExecutionPort
                               session states: running|permission_wait|completed|
                                               failed|cancelled|ambiguous|orphaned
        ▲ (neutral backend protocol + exact-type factory allowlist)
        │
Neutral turn seam  [NEW]       SupervisorTurnBackend / SupervisorTurnResult
                               transport vocabulary: accepted|completed|failed|
                                                     cancelled|timed_out|unknown
        ▲                                          ▲
        │                                          │
Backends            fake (default, no ARS import)  ArsdSupervisorBackend  [NEW]
                                                          │
Private identity    ArsdRunBindingLedger [NEW, durable]   │  ArsdClientFacade
                    (task_id, session_id, dispatch_ref)   │  (7 ops, v3 envelope)
                        -> pending intent (pre-submit)    │
                        -> accepted binding (post-ack)    ▼
                                                   operator-managed arsd daemon
```

Two invariants shape every stage:

- **Foreign data never becomes canonical data.** `run_id`, `ars_session_id`, `next_from_seq`, and remote `error.message` live in private, `repr=False`, non-serializable fields. Public surfaces carry only Sachima-derived `run_ref` / `source_ref` / `artifact_ref` and Sachima-owned stable codes.
- **Absence of observation is not evidence of failure.** Disconnects, unreadable replies, and daemon restarts mark the *observation* failed and leave canonical state untouched.

### R-1 — Durable home for the private binding ledger

**Problem.** Spec §7.3 requires a restart-safe private binding. `TaskEventLog` is forbidden for raw ids (Spec §9.5), and the existing `LiveProgressSourceBindings` (`sachima_supervisor/runtime_spine/live_progress_sources.py:249-267`) is an **in-memory** store — `_bindings: dict[...] = field(default_factory=dict, init=False)`. Neither can hold the binding.

**Decision.** A new, purpose-built durable module: `sachima_supervisor/runtime_spine/arsd_run_binding_ledger.py`.

- One host-owned private JSON file, absolute, outside the tracked repo, supplied by a new `ArsdSupervisorConfig.binding_ledger_path` (private, `repr=False`, validated by the existing `_private_abs_path` boundary).
- Writes are atomic: serialize → write temp sibling → `os.replace`. A torn or unparseable file fails closed with `runtime_invalid_arsd_binding`; it is never silently reset.
- Record fields: public `task_id`, `session_id`, `dispatch_ref`, `request_id`, `run_ref`, `payload_digest`, `state` (`pending` | `accepted`), and `resolver_refs` — the minimum immutable policy/workspace/grant/config refs needed to rebuild the frozen payload (Spec §7.3.1); plus, **only once accepted**, `accepted_at` and the private `run_id`, `ars_session_id` (`repr=False`, absent from `as_dict()`). No prompt or payload text, credential value, socket path, or remote text is persisted in either state.
- **Two states, one record.** The record is written `pending` **before** the first socket submit and **finalized in place** to `accepted` by a validated ack; there is never a second record for the same key, and no accepted record exists without a preceding pending one (Spec §7.3.1). This is what makes a lost ack recoverable: an ack-only write leaves nothing durable to prove which `request_id` and digest were in flight. The ledger half is tested in P2-c; the genuinely-lost-ack path is P4-e, where the submit seam exists.
- Responsibilities stay split: the **ledger** owns durable identity; `LiveProgressSourceBindings` keeps owning the in-memory read-model position (`source_kind`, `artifact_ref`/`run_ref`, `last_seen_cursor`). This is not duplication — one is identity, one is cursor state.

**Restart-safe test (non-vacuous by construction).** `test_second_ledger_instance_resumes_without_redispatch`: instance A writes a pending intent and finalizes it into an accepted binding; instance A is dropped; a **fresh** `ArsdRunBindingLedger` is constructed over the same path with a facade double whose `submit` raises on call; `resolve()` returns the identical `run_id`/`ars_session_id` and observation proceeds. If any code path re-dispatched, the facade double fails the test.

### R-2 — One key contract

**Problem.** Spec §7.1 derives `request_id` from `(task_id, session_id, dispatch_ref)`; Spec §7.3 writes the ledger key as `(task_id, dispatch_ref)`.

**Decision.** The ledger key is the **full triple**, identical to the `request_id` derivation inputs. Source basis:

- `derive_arsd_request_id(task_id, session_id, dispatch_ref)` — `sachima_supervisor/runtime_spine/arsd_socket_contract.py:521` — takes exactly three components.
- The dispatcher requires a `sess_`-prefixed Sachima spine session id (`agent_run_supervisor_turn_dispatcher.py:105-108`), and `AgentRunSupervisorPort.create_or_attach` can mint a **new** spine `session_id` for the same `task_id` across a reconstruct/attach cycle. `(task_id, dispatch_ref)` is therefore not unique over a task's lifetime and would alias two distinct dispatches onto one binding.

`request_id` is stored on the record as a **derived witness**, not a second key. The redundancy is exactly what makes the contract checkable.

**Tests.** `test_binding_key_is_exactly_the_request_id_derivation_inputs` — for every stored record, `derive_arsd_request_id(*key) == record.request_id`, and a record whose stored `request_id` disagrees fails closed on read. `test_same_dispatch_ref_under_two_spine_sessions_binds_two_records` — the alias the two-component key would have created is proven absent.

### R-3 — `turn_dir` removal cannot pass vacuously

**Problem.** Introducing a neutral result type while the old field survives would satisfy A-19's letter and none of its intent. Note also that `SupervisorTurnResult` does **not exist** at this baseline — the concrete type is `LibraryTurnResult`, and it carries `turn_dir`.

**Decision.** An enumerated coupling inventory (§9.1, table C) plus a repo-wide absence guard:

`test_no_turn_dir_reference_in_runtime_source` — greps every `*.py` under `sachima_supervisor/`, `gateway/`, and `scripts/` for the **bare identifier** `turn_dir` (exact semantics in §9.2) and asserts zero hits. Adding a new neutral type without deleting `LibraryTurnResult.turn_dir` (`agent_run_supervisor_library_backend.py:417`), the dispatcher's `result.turn_dir` (`agent_run_supervisor_turn_dispatcher.py:331`), the facade tuple (`:889`), or the activity's `Path(outcome.turn_dir).iterdir()` (`activity_session_real_execution.py:482`) fails that test. All four sites are closed in P3, so the guard never waits on a later stage.

The concrete-type couplings are covered by the same stage: `type(backend) is not AgentRunSupervisorLibraryBackend` (`agent_run_supervisor_turn_dispatcher.py:261`), `type(result) is not LibraryTurnResult` (`:396`), and the frozen bundle's `backend: AgentRunSupervisorLibraryBackend` + `__post_init__` type check (`agent_run_supervisor_execution_binding.py:67,77`).

### R-4 — `MAX_ERROR_MESSAGE_CHARS` in the drift-lock decision

**Problem.** Spec §5.2 names four bounds Sachima "mirrors and drift-locks", but B-4 enumerates only five constants and omits `MAX_ERROR_MESSAGE_CHARS`. Sachima also discards remote `message` entirely (§9.5, §13.1), so a naive mirror would have no consumer.

**Decision: mirror it and drift-lock it**, with exactly one real consumer so it is not speculative surface.

- Add `ARSD_MAX_ERROR_MESSAGE_CHARS = 512` to the mirror set; drift-lock it against `agent_run_supervisor.arsd.protocol.MAX_ERROR_MESSAGE_CHARS` alongside the other five (present at `arsd/protocol.py:34` in the 0.7.1 baseline; the symbol, not the line, is the anchor — §4.0).
- Consumer: the adversarial **discard witness**. `test_remote_error_message_at_the_contract_maximum_is_fully_discarded` builds a client-error double whose `message` is a leak-marker string of exactly `ARSD_MAX_ERROR_MESSAGE_CHARS` characters — the true wire maximum — and proves not one byte reaches any exception message, repr, projection, or serialized surface. The mirror keeps that fixture pinned to the real maximum if ARS ever raises the bound.

This makes §5.2 and B-4 consistent rather than leaving a documented-but-unmirrored constant.

**0.7.6 amendment.** The same "mirror it, and give it exactly one real consumer" rule now governs the constants the calibration adds, so none of them becomes speculative surface:

| Constant | Real consumer that makes the mirror non-vacuous |
|---|---|
| `RunLimits.turn_timeout_seconds` default (`21600.0`), inclusive `LIMIT_TURN_TIMEOUT_SECONDS_MAX` (`604800.0`) | Per-policy run-limit validation in P1-l — a `run_limits_by_policy_ref` entry above the maximum fails closed at config construction |
| `STRUCTURAL_MAX_RUN_EVENT_BUDGET_BYTES` | The `server_info` limits ceiling check in `validate_arsd_server_info` (Spec §5.3) |
| Negotiated `max_run_event_budget_bytes` | The admission-product pre-check in P1-l, wired in P4-a to the value from **each new admission's own** `server_info` negotiation |

The 4 GiB deployment default is deliberately **not** mirrored as a constant: it has no valid consumer, because asserting it would fail against any correctly reconfigured daemon (Spec §5.3.1).

### R-5 — `session_list` response shape

**Fact (0.7.1 baseline provenance, `arsd/handlers.py:1477-1488` — line retained per §4.0, symbol is the anchor).** `_session_list` returns `{"sessions": [ <session_view>, ... ]}`. `_session_view` is exactly `{session_id, owner, namespace, agent_id, profile_id, created_at, updated_at, last_effective_model, last_effective_effort, quarantine}`. P1's drift lock re-confirms this ten-key set against the installed 0.7.6 distribution; the Spec's non-drift block (§4.4.1) expects no change here, and if the distribution disagrees the distribution wins.

**Decision.** Two validators, not one:

- `validate_arsd_session_view(payload) -> ArsdSessionView` — exact ten-key set, `quarantine` is `None` or exactly `{reason_code, source_run_id, recorded_at}` with `reason_code` in the closed five-member mirror (`DISPATCH_OBSERVATION_LOST`, `DISPATCH_WITHOUT_TRUSTWORTHY_TERMINAL`, `UNTRUSTED_TERMINAL_EVIDENCE`, `SWITCH_ROLLBACK_UNPROVEN`, `RECONCILED_DISPATCH_WITHOUT_TERMINAL`), drift-locked against `agent_run_supervisor.session.QUARANTINE_REASON_CODES` and `QUARANTINE_EVIDENCE_FIELDS`.
- `validate_arsd_session_list(payload) -> tuple[ArsdSessionView, ...]` — top-level key set exactly `{"sessions"}`, value a `list`, each element through the view validator.

**Negative tests that pin the top level** (`test_session_list_rejects_a_bare_session_record`, `test_session_list_rejects_a_non_list_sessions_value`, `test_session_list_rejects_extra_top_level_keys`) plus `test_session_list_accepts_an_empty_session_page`. A bare session record at the top level is a protocol violation, never a tolerated shape.

`last_effective_model` / `last_effective_effort` are validated as **observations of the Session's last Run** and nothing more (Spec §6.4). `test_last_effective_values_are_never_read_back_into_request_construction` proves no code path feeds them into `build_arsd_submit_payload`, which is what keeps the per-Run override (Spec §5.5.4) from silently degrading into a Session-level setting.

### R-6 — Transport-terminal vocabulary vs. Sachima canonical vocabulary

**Fact.** These are four distinct closed vocabularies in the current tree:

| Layer | Vocabulary | Source |
|---|---|---|
| ARS Native ACP terminal | `completed`, `failed`, `cancelled`, `timed_out`, `unknown` | `agent_run_supervisor.exit_classifier.AgentRunStatus` (exactly five members) |
| Transport-neutral (new seam) | `accepted`, `completed`, `failed`, `cancelled`, `timed_out`, `unknown` | Spec §8.3 |
| Sachima port / session state | `running`, `permission_wait`, `completed`, `failed`, `cancelled`, `ambiguous`, `orphaned` | `execution_port.py:21-34` |
| **Sachima canonical status** | `created`, `running`, `permission_wait`, `completed`, `failed`, `cancelled` | `events.py:156-158` (`STATUS_VALUES`; `:159` is the separate `TERMINAL_STATUSES`) — **no `timed_out`, no `unknown`, no `ambiguous`** |

**Decision.** The mapping is explicitly three-hop, and the boundary between hop 2 and hop 3 is the thing under test:

```text
ARS terminal      transport-neutral      port session state      canonical status
completed    ->   completed         ->   completed          ->   completed
failed       ->   failed            ->   failed             ->   failed
cancelled    ->   cancelled         ->   cancelled          ->   cancelled
timed_out    ->   timed_out         ->   failed             ->   failed
unknown      ->   unknown           ->   ambiguous          ->   failed
```

The last column already exists: `agent_run_supervisor_port.py:88` maps backend `ambiguous` to session state `ambiguous`, and `_terminal_event_body` (`:788-790`) projects that as canonical `failed`. So `timed_out` and `unknown` converge on canonical `failed` through **different** session states — observable at `SessionStatus.state`, which is exactly what makes A-12's "proven independently" satisfiable.

**Tests.** `test_transport_terminal_vocabulary_is_disjoint_from_canonical_status_values` (asserts `timed_out`/`unknown`/`accepted` are absent from `events.STATUS_VALUES`, so a transport token can never be appended as a canonical status), and `test_each_ars_terminal_maps_through_all_three_hops` — one parametrized row per terminal asserting the transport token, the resulting `SessionStatus.state`, and the canonical `TaskEventLog` status, all three.

## 8. Stage P2 — Durable private binding ledger

**Objective.** Restart-safe `(task_id, session_id, dispatch_ref)` → `(run_id, ars_session_id)` binding, durable, private, and never on a canonical or public surface — written as a pending submission intent **before** the submit and finalized in place after the ack, so a lost ack is recoverable rather than unprovable.

### P2 tasks

**P2-a — New module** `sachima_supervisor/runtime_spine/arsd_run_binding_ledger.py` per R-1: `ArsdRunBinding` (frozen, `__post_init__` allowlist, `state` ∈ {`pending`, `accepted`}, `resolver_refs`, private `run_id`/`ars_session_id`, `as_dict()` refs-only), `ArsdRunBindingLedger(path)` with the two-phase `begin_pending()` / `finalize_accepted()` pair that replaces a single-shot post-ack `bind()`, plus `resolve()` / `resolve_pending()` / `resolve_for_task()` / `record_session_id()`, `derive_arsd_binding_key()`, `derive_run_ref()` (`run_<digest8>`, never the raw id), module-local stable codes `RUNTIME_INVALID_ARSD_BINDING` / `RUNTIME_ARSD_BINDING_CONFLICT`, and `ARSD_BINDING_STABLE_CODES`. No new stable code is minted for the recovery digest mismatch — it is a binding conflict and reuses `RUNTIME_ARSD_BINDING_CONFLICT`.

**P2-b — Semantics.**

- `begin_pending()` writes the intent atomically and returns only once the write has landed, so P4-a can call it **before** the first socket submit. It is idempotent on the full key with byte-equivalent material; a same-key pending write with a different `request_id`, `payload_digest`, or `resolver_refs` fails closed with the conflict code and never overwrites (Spec §7.1: no new id, no resubmit).
- `finalize_accepted()` adds `run_id`, `ars_session_id`, and `accepted_at` to the **existing** pending record in place, atomically, and flips `state` to `accepted`. Finalizing a key with no pending record, or one already accepted with different material, fails closed with the conflict code. Exactly one logical record per dispatch, always (Spec §7.3.1).
- A record left `pending` is **fail-closed** for that dispatch: `resolve()` reports it unresolved rather than inferring acceptance, and the ledger never deletes it, never finalizes it by inference, and never triggers a replay. Only the explicit recovery entry point (P4-a) may act on it.
- `record_session_id()` writes the ARS session id on the **first** turn only; a later differing id fails closed — a Session is never silently replaced (Spec §7.3 rule 3).
- At most one **active** run per `(task_id, session_id)` binding, enforced Sachima-side (Spec §7.4). The dispatcher's single-flight window covers submit/admission only and is documented as not a run-duration lock.
- `retry_of_run_id` is only ever set through an explicit recovery entry point, never from a timeout or disconnect path.

## 10. Stage P4 — `arsd` backend: submit, observe, cancel, terminal truth

**Objective.** A default-off `arsd` backend that submits once, observes honestly, cancels precisely, and never fabricates an outcome.

### P4 tasks

**P4-a — New module** `sachima_supervisor/runtime_spine/arsd_supervisor_backend.py`:

- `ArsdSupervisorBackend(config, facade, ledger)` — constructing it *is* the gate: `require_enabled_arsd_supervisor_config` fails closed unless `enabled` is exactly `True`.
- **Negotiation.** `server_info` through `validate_arsd_server_info` at composition, **and again immediately before every new admission** — negotiate → pre-check → submit is one sequence per new Run, with nothing in between that could change the budget under it (Spec §5.3.1 consequence 1). A failure is a single stable backend-unavailable verdict; there is no fallback to library, CLI, `acpx`, or another API version. Each new admission feeds P1-l's pre-check the `max_run_event_budget_bytes` from **its own** negotiation: never defaulted, never guessed, and never carried over from composition or from an earlier admission. The same-request recovery path below negotiates nothing.
- **Submit.** `run_turn` negotiates, derives `request_id`, builds the payload, records the digest, runs the current-budget admission pre-check, **writes the pending submission intent via `begin_pending()` and waits for that write to land**, and only then submits. On a validated three-key ack it calls `finalize_accepted()`, which adds `run_id`, `ars_session_id`, and `accepted_at` to that **same** record in place — never a second record (Spec §7.3.1). It returns `supervisor_status="accepted"` and does **not** block until the AGENT terminates (Spec §8.3). The pre-check runs **before** every **new** submit against that admission's own negotiated budget, so a run-limits choice the daemon would refuse fails closed without spending a submit. It is a **new-admission** guard only and is not applied to the recovery path below (Spec §5.6.2, §5.3.1 consequence 3).
- **Create vs. reuse.** First turn omits `session_id`; later turns of the same task pass the recorded id verbatim. A quarantined or unknown Session is never auto-healed, auto-recreated, or retried into.
- **Per-Run model/effort.** Every Run — including every reuse turn — re-resolves its `(requested_model, requested_effort)` pair from the policy maps. The pair is never cached onto the Session binding and is never derived from `last_effective_model` / `last_effective_effort` (Spec §5.5.4). The backend claims nothing about ARS-internal selector switching, and no offline test is worded so as to imply the effective configuration was read back (gates E-9 / E-10).
- **Observe.** `status()` reads `run_status` and applies the R-6 three-hop mapping. An observation failure returns a transient stable code and mutates nothing.
- **Cancel.** `kill()` issues exactly `run_cancel(active_run_id)` — never a Session operation. `cancelled` projects only on trusted terminal evidence; otherwise a bounded re-query, then `ambiguous` / observation-failure. A successful cancel is never claimed unproven.
- **Permissions.** `signal()` stays fail-closed in `arsd` mode; no `permission_wait` → `running` transition is invented (Spec §10.6). Grants stay on the read/search allowlist. Sachima supplies a frozen grant and never an ACP mode — at 0.7.6 the mode is derived from that grant (Spec §10.6.1).
- **Permission-violation terminal.** A `PERMISSION_VIOLATION` terminal is **trusted terminal evidence of a failure**: it moves canonical status through the ordinary terminal path, not the contained-internal path and not observation loss. It is non-retryable — no automatic retry, no new `request_id`, no `retry_of_run_id` — and it does **not** quarantine or replace the Session, which stays reusable for the next turn (Spec §10.7).
- **Indeterminate submit, including a lost ack.** Maps to `runtime_arsd_submission_indeterminate` and leaves the pending submission intent exactly as written, **fail-closed** — not deleted, not finalized by inference, not replayed. No automatic replay, no new `request_id`; nothing in the timeout, disconnect, restart, or reconciliation paths may act on the intent by itself (Spec §7.3.1, §10.3).
- **Explicit recovery entry point.** A separately invoked method — never reachable from an automatic path — that: reads the pending intent; rebuilds the payload through the **same resolver** from the intent's `resolver_refs`; and **fails closed with `RUNTIME_ARSD_BINDING_CONFLICT` and zero socket calls** if the rebuilt payload's digest differs from the recorded `payload_digest`, because Sachima can no longer prove byte-equivalence. On a match it re-sends the **identical** `request_id` with that byte-equivalent frozen payload even if the negotiated event budget has changed since the original submit; the payload is never re-tuned to the new budget (Spec Δ-12). Because it carries the same `request_id` and the recorded digest, it performs **no negotiation** and **bypasses the current-budget pre-check**, resending unchanged — ARS resolves it against its durable admission record (Spec §5.3.1 consequence 3, §5.6.2). The resulting durable ack calls `finalize_accepted()` on that **same** intent, exactly once. The bypass is keyed on `request_id` **and** digest together; any other request, including a new one built from the same run-limits entry, negotiates afresh and is pre-checked as usual.
