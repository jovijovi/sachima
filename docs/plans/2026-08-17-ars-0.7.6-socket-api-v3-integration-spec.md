## 2. Business objective and success definition

### 2.1 Objective

Sachima must be able to run real external AGENT work through an **operator-managed** `arsd` daemon over a local Unix socket, while Sachima remains the authority for everything the product is judged on.

The division of authority is the whole point of the integration:

| Authority | Owner |
|---|---|
| `task_id`, durable workflow state, `TaskEventLog` sequence, Status Projection, user-visible business status | **Sachima** |
| Run execution, Session durability, ACP permission mediation, terminal evidence trust, local artifact storage, daemon lifecycle | **ARS / operator** |

ARS is an execution and evidence boundary. It is never a source of Sachima's canonical sequence, and never a source of user-visible text.

### 2.2 Success definition

The integration is successful when all of the following hold:

1. One admitted Sachima turn produces exactly one durable ARS Run, identified by a Sachima-derived idempotent `request_id`.
2. Sachima privately binds `(task_id, dispatch) → (run_id, session_id)` and can resume observation of that Run after a process restart without re-dispatching.
3. Later turns of the same task reuse the same durable ARS Session; a Session is never closed by Sachima and never silently replaced.
4. Sachima's user-visible status derives only from trusted Run terminal evidence or from Sachima's own state — never from a socket-level event, a foreign cursor, or a raw remote message.
5. Observation loss (disconnect, daemon restart, unreadable reply) never becomes a fabricated Run failure and never mutates canonical task state.
6. `kill` cancels the active Run only, and reports `cancelled` only on trusted terminal evidence.
7. No prompt, model text, tool payload, stderr, credential, private socket path, raw remote error, or daemon run directory reaches any Sachima event, projection, log, serialized state, or user surface.
8. Selecting the retired `library` mode fails closed with a stable migration error naming the supported choices.

### 2.3 Non-success (explicitly not a goal of the integration itself)

Turning `arsd` on, running a real AGENT, wiring Gateway, or shipping a user-facing feature. Those are separate approvals downstream of a working, proven contract.

## 5. API v3 protocol and closed contracts

### 5.1 Closed operation set

Socket API v3 is the **only** supported wire version. Exactly seven operations exist:

```text
server_info  submit  run_status  run_events  run_cancel  session_status  session_list
```

There is no `session_close`. Sachima must model the operation set as a closed frozen set and must never send an operation outside it.

### 5.2 Envelope and framing

```text
request  : {api_version: 3, op: <one of the seven>, request_id: <[A-Za-z0-9._-]{1,128}>, payload: {...}}
result   : {request_id, result: {...}}
error    : {request_id | null, error: {code, message}}
```

Bounds Sachima mirrors and drift-locks: frame ≤ 1 MiB, prompt ≤ 256 KiB, JSON container nesting ≤ 64, error message ≤ 512 chars.

The version verdict is taken on the **envelope**, before the operation is resolved. There is no per-operation version matrix and no drain window.

### 5.3 `server_info` negotiation

Result shape is exactly:

```text
version                 # package version string
api_version             # 3
supported_api_versions  # [3]
operations              # the sorted seven
limits: {max_concurrent_runs, max_frame_bytes, max_prompt_bytes,
         events_page_limit, event_follow_queue_size,
         max_run_event_budget_bytes}          # sixth key, added in 0.7.5
```

The **top-level** key set is still exactly five. Only the nested `limits` key set grew, from five to six (Δ-8).

Sachima's `server_info` negotiation — run before the first submit of a composed backend, and run **again immediately before every new admission** (§5.3.1 consequence 1) — verifies:

| Check | Verdict on failure |
|---|---|
| Result is a mapping whose key set is exactly the five top-level keys above | `runtime_arsd_protocol_violation` |
| `limits` key set is exactly the **six** limit keys; every value a non-bool int | `runtime_arsd_protocol_violation` |
| `version == expected_package_version` (`0.7.6`) | `runtime_arsd_version_mismatch` |
| `api_version == 3` | `runtime_arsd_version_mismatch` |
| `supported_api_versions == (3,)` exactly | `runtime_arsd_version_mismatch` |
| `operations` equals the closed seven-operation set exactly | `runtime_arsd_version_mismatch` |
| `max_frame_bytes` / `max_prompt_bytes` equal the mirrored protocol constants | `runtime_arsd_version_mismatch` |
| `max_concurrent_runs`, `events_page_limit`, `event_follow_queue_size` are usable and bounded | `runtime_arsd_version_mismatch` |
| `max_run_event_budget_bytes` is a positive non-bool int, at most the mirrored `STRUCTURAL_MAX_RUN_EVENT_BUDGET_BYTES` | `runtime_arsd_version_mismatch` |

A five-key `limits` block — the 0.7.1 shape — is a **protocol violation** against a 0.7.6 daemon, not a tolerated older peer: there is no compatibility window and no per-operation version matrix (§5.2). A seventh key is equally a violation.

Only the exact mirrored values reach the repr-safe observation object, so no remote string survives into a diagnostic surface. A mismatch is a single stable backend-unavailable verdict. **There is no silent fallback** to library, CLI, `acpx`, or a different API version.

#### 5.3.1 `max_run_event_budget_bytes` — default vs. runtime vs. maximum

Three distinct numbers live near this key, and the Spec keeps them distinct because mislabelling any one of them produces a test that either passes vacuously or fails on a correctly configured host.

| Number | What it is | How Sachima may use it |
|---|---|---|
| `4 * 1024 * 1024 * 1024` bytes (4 GiB) | The **ARS deployment default**, raised from 1 GiB in 0.7.5 | Documentation only. Sachima never equality-asserts it against a live daemon, and never treats it as a floor, a ceiling, or a contract constant |
| The value in `server_info.limits` | The **negotiated runtime value** of the daemon actually answering, which the operator may configure to anything valid | The one authority for admission arithmetic (§5.6). Re-negotiated for each new admission and used from *that* negotiation, never assumed and never carried forward |
| `STRUCTURAL_MAX_RUN_EVENT_BUDGET_BYTES` == `LIMIT_MAX_EVENT_BYTES_MAX * LIMIT_MAX_EVENTS_MAX` | The **structural maximum**, derived from the two per-field maxima | Mirrored and drift-locked as a maximum (§14.2 B-12). It is not a default and must never be described as one |

Three operational consequences follow directly:

1. **A daemon restart or an operator reconfiguration can change the negotiated value.** Every **new** admission therefore performs a **fresh `server_info` negotiation immediately before** its budget pre-check and its submit, and pre-checks against the value that negotiation returned (consequence 3). Negotiate → pre-check → submit is one sequence per new admission, with nothing in between that could change the budget under it. A budget negotiated for an earlier Run is not authority for a later one: no cached value — from composition, from a previous new admission, or from any earlier preflight — may be reused to admit a new Run, and a stale value is a reason to re-negotiate, never a reason to submit anyway.
2. **A retry must not be re-tuned to a new budget.** Duplicate retries resolve against their durable admission records across daemon restarts and configured budget changes (Δ-12). So the §7.1 recovery path — identical `request_id`, byte-equivalent payload — remains correct across such a change, and Sachima must **not** "helpfully" adjust `limits` in the retry payload to fit a newly negotiated budget: that breaks byte-equivalence and earns `IDEMPOTENCY_CONFLICT`, which §7.1 requires Sachima to fail closed on.
3. **The current-budget pre-check governs new admissions only.** §5.6.2's `max_event_bytes * max_events <= max_run_event_budget_bytes` check is an *admission* guard: it runs before every **new** submit, against that admission's own fresh negotiation. A recovery attempt for an uncertain submission — the **same `request_id`** carrying the **byte-equivalent frozen payload**, proven by the `arsd_submit_payload_digest` recorded in that request's durable pending submission intent (§7.3.1) — **bypasses both that pre-check and the fresh negotiation that precedes it**, and resends the frozen payload unchanged. The question such an attempt asks is not "may this be admitted under today's limits?" but "what happened to the submission already admitted under yesterday's?", and ARS answers it from the durable admission record (Δ-12). Applying the current-budget pre-check there would block the exact durable-idempotency lookup ARS exists to resolve, and would leave an already-admitted Run permanently unobservable whenever the operator lowered the budget after admission.

   This is **not** a general bypass. It is available only when the `request_id` **and** the payload digest both match the recorded submission. Anything else — a new dispatch, a re-derived `request_id`, or a payload differing by a byte — is a **new** admission: it negotiates afresh and is pre-checked against *that* budget like any other. A stale limit set never becomes admissible by being replayed, and the bypass never widens beyond the one already-admitted request it resolves.

### 5.5 Per-Run configuration override — `requested_model` / `requested_effort`

#### 5.5.1 What this is, and what it is not

`AgentRunRequest` has carried per-Run `requested_model` and `requested_effort` since before 0.7.6. **This is not new in 0.7.6**, and the request shape did not drift (§4.4.1). Sachima's D0/D1 submit builder already resolves both from the closed `model_by_policy_ref` / `effort_by_policy_ref` maps, and `limits` from `run_limits_by_policy_ref`. What this section adds is not a new field; it is the set of obligations that make the existing field set *load-bearing* instead of decorative.

The scope is **exactly two values: model and effort**. This is not a general configuration-injection channel. Sachima does not send arbitrary ARS configuration per Run, does not forward operator profile settings, and does not gain a way to override anything else.

#### 5.5.2 The maps are the only source

1. Every submit carries an explicitly resolved `(requested_model, requested_effort)` pair, produced from the per-policy maps for that Run's policy refs.
2. There is no implicit fallback: Sachima never relies on a daemon-side or profile-side default for these two values, and never sends an unset/`None` passthrough.
3. A policy ref with no mapped model or no mapped effort **fails closed Sachima-side**, before any socket call, with the stable invalid-request/invalid-config code — never a submit with a hole in it.

#### 5.5.3 Request literals are not effective-configuration proof

Before Prompt, ARS sets `requested_model` / `requested_effort` and reads them back **exactly**. Any mismatch **fails the Run** with the categorical stop reason `CONFIG_FIDELITY`, and **Prompt is not sent**. There is therefore no Run that quietly executes under a substituted pair: either the read-back matched, or the Run failed before any agent work began.

**Sachima's own literal is not evidence.** "We sent `requested_model = X`" does not prove the Run executed under X; only ARS's read-back does. The fail-closed mismatch outcome is what makes that operational rather than rhetorical — the mismatch case has a name and a terminal, so a Sachima request literal never has to be trusted in its place.

Three obligations follow:

1. A `CONFIG_FIDELITY` failure is a **Run failure on trusted terminal evidence**, handled through the ordinary terminal path (§10.1) — not observation loss (§10.2) and not the contained-internal path (§10.5). The stop reason is a categorical *reason*, not a sixth member of the five-member terminal status vocabulary (§6.5), and Sachima adds **no** branch keyed on the token: a failed Run is `failed` whatever the reason.
2. Because Prompt was never sent, Sachima must claim **no** agent work for such a Run and must not auto-recover from it: no automatic retry, no new `request_id`, no `retry_of_run_id` (§7.1, §10.3). Re-running under a corrected configuration is an explicit decision.
3. No Sachima surface — status, projection, log, serialized state, or test assertion — may present a built request literal as the Run's effective configuration. `session_status`'s `last_effective_*` values are observations of a *past* Run (§6.4) and are not a substitute either.

The Spec therefore splits the obligation:

- **Offline, provable now:** that request *construction* is correct — the right pair, from the right maps, on every Run, failing closed when unresolvable — and that Sachima's handling of a *reported* `CONFIG_FIDELITY` terminal is the ordinary trusted-failure path with no effective-configuration claim attached.
- **Live, not provable offline:** that ARS set and read back exactly those values before Prompt for a real Run, and that a real mismatch fails with `CONFIG_FIDELITY` before Prompt. That is an observation obligation, carried as open gate E-9, and no offline test may be worded so as to imply it has been met.

Sachima does **not** perform ARS-internal selector or profile switching, and must not claim to. It states a requested pair per Run; ARS owns what that resolves to internally.

#### 5.5.4 Same-Session switching is a per-Run property

A later Run reusing the same ARS Session may request a **different** `(model, effort)` pair. Model and effort are properties of the Run, not of the Session. Three rules follow:

1. Sachima re-resolves and re-sends the pair on **every** Run, including every reuse turn.
2. Sachima never caches the first turn's pair onto the Session binding, and never derives a later Run's pair from an earlier one.
3. `session_status`'s `last_effective_model` / `last_effective_effort` (§6.4) are **observations of the last Run**. They are not the next Run's configuration, not an input to request construction, and not a substitute for the read-back of the Run actually in question.

Because the exact per-Run values must be re-proven for each Run, real same-Session switching is carried as a **later, separately approved canary/evidence gate** (E-10), not as an offline claim.

#### 5.5.5 Non-vacuous offline obligation

The offline proof must be constructed so that a builder which dropped the override, hard-coded one pair, or cached the first pair would fail:

- The mirrored `AgentRunRequest` field set and required/optional split — drift-locked against the real dataclass (§14.2 B-6) — explicitly includes `requested_model` and `requested_effort`. A rename or removal upstream breaks the lock rather than silently emptying the override.
- Two different policy refs resolved under one binding must produce two payloads that differ in **exactly** those two fields and are identical elsewhere. A builder ignoring the refs produces identical payloads and fails; a builder leaking the refs into other fields produces a wider diff and also fails.
- A second Run reusing the same Session under a newly resolved pair must carry the new pair, with no code path reading `last_effective_model` / `last_effective_effort` back into construction.

These are acceptance rows A-25 and drift lock B-6 (§14).

### 5.6 Run limits: mirrored defaults, mirrored maxima, and the admission product

Sachima mirrors `RunLimits` defaults and the `LIMIT_*` maxima rather than choosing numbers of its own. Every value below is a mirror, drift-locked against the installed distribution (§14.2 B-11); **no arbitrary Sachima constant is introduced anywhere in this Spec.**

| Constant | Value at 0.7.6 | Note |
|---|---|---|
| `RunLimits.turn_timeout_seconds` default | `21600.0` s (6 h) | Raised from `600.0` in 0.7.2 (Δ-1) |
| inclusive `LIMIT_TURN_TIMEOUT_SECONDS_MAX` | `604800.0` s (7 d) | Raised from `86400.0` in 0.7.2 (Δ-2); inclusive, so the maximum itself is admissible |
| startup-timeout default and maximum | unchanged from 0.7.1 | Recorded so the timeout move is not over-read (Δ-3) |
| cancel-grace default and maximum | unchanged from 0.7.1 | As above |

#### 5.6.1 What the 6-hour default does and does not change

It changes **no Sachima contract**. `run_turn` for `arsd` is a submit that returns on durable acceptance (§8.3) and never blocks on terminal truth, so a longer permitted turn does not lengthen any Sachima call.

It does change what "still running" plausibly means over a task's life. Two rules keep that honest:

- Sachima must not impose a shorter deadline of its own and convert its expiry into a `timed_out` or `failed` verdict. A terminal status ARS did not produce is a fabricated outcome, which §10.1 forbids. Absent terminal evidence with progress present stays `running`; absent evidence with no observation stays observation loss (§10.2).
- The bounded re-query window after a cancel (§10.4) is Sachima's own policy about *how long it waits to observe an outcome*, and is unrelated to — and must not be scaled from — the turn timeout. Conflating them would make a cancel look successful or failed on a schedule ARS never agreed to.

#### 5.6.2 Per-field validity does not imply admissibility

`RunLimits` keeps structural per-field maxima, **and** the daemon separately checks at admission that

```text
max_event_bytes * max_events <= max_run_event_budget_bytes
```

(Δ-10). A `run_limits_by_policy_ref` entry can therefore satisfy every per-field maximum and still be refused. Sachima performs the same pre-check **before** submitting, against the budget returned by the fresh negotiation that immediately precedes *this* new admission (§5.3.1 consequence 1), and fails closed with the stable invalid-request code rather than spending a submit to learn the answer. This is acceptance row A-23.

**Scope: new admissions only.** The pre-check gates *admission of a new request*. It is **not** applied to a recovery attempt for an uncertain submission that reuses the same `request_id` with the byte-equivalent frozen payload: that attempt performs no new-admission negotiation, bypasses the pre-check, and resends unchanged, and ARS resolves it against its durable admission record (§5.3.1 consequence 3, §7.3.1, Δ-12, A-24). Otherwise a budget the operator lowered after admission would block Sachima from ever learning the fate of a Run the daemon already holds. The bypass is keyed on the matching `request_id` **and** payload digest together; every other request — including a new one built from the same `run_limits_by_policy_ref` entry — negotiates afresh and is pre-checked against *that* budget, failing closed before submit if the product exceeds it.

The pre-check is a guard, not a re-implementation of daemon policy: the daemon remains the authority, and a refusal Sachima did not predict is still handled through the ordinary error mapping (§13).

## 6. Session no-close and Run lifecycle model

### 6.1 The model

**Runs terminate. Sessions do not close.**

- A **Session** is durable conversation continuity with one registered agent. It has identity, binding, and last-use observations — and deliberately **no lifecycle state to project**. It is never closed, by Sachima or by anyone.
- A **Run** is the terminal, disposable unit of work. Exactly one Run occupies a Session at a time; a concurrent Run against the same Session is refused with `SESSION_BUSY`.
- **Quarantine** is separate continuity evidence, not a lifecycle state. A quarantined Session still exists; it is refused for *reuse*.

### 6.2 Create vs. reuse — the only Session decision

The whole Session choice is the presence of `request.session_id`:

| Caller statement | Wire form | Daemon behavior |
|---|---|---|
| "I have no Session" | **key omitted** | Create one new durable Session, run its first Run |
| "Reuse exactly this Session" | key present, valid id | Existing-only reuse; never falls back to create |
| "My Session is null" | key present, `null` | **`INVALID_REQUEST`**, refused before any storage access |

This is a correctness rule, not a style rule: collapsing absent and present-null would let a Sachima code path whose id lookup returned `None` silently start a *second* conversation against the same agent. Sachima's submit builder must therefore construct the request dict with the `session_id` key **absent** on create — not present-and-`None`.

Sachima must never derive a "reuse mode" flag on the wire. There is no `session_reuse` field in schema 3.

### 6.3 Session id acquisition

Sachima learns the Session id from the **submit ack**, which carries it directly (§7.2). Sachima must not derive it, guess it, or reconstruct it from a `run_id` convention. The daemon's internal derivation for a create Run is daemon-private.

The id must satisfy `[A-Za-z0-9][A-Za-z0-9_\-]*` before Sachima sends it back on a reuse turn; anything else is a Sachima-side invalid-request failure, never a socket call.

### 6.4 Session state Sachima may observe

`session_status` / `session_list` project identity, last-use observations, and optional quarantine evidence:

```text
session_id  owner  namespace  agent_id  profile_id  created_at  updated_at
last_effective_model  last_effective_effort  quarantine
```

`quarantine` is `null` or exactly `{reason_code, source_run_id, recorded_at}` with `reason_code` from a closed five-member vocabulary. It is categorical by construction: no exception text, no agent text, no path.

`last_effective_model` and `last_effective_effort` are **observations of the Session's last Run**, not configuration for the next one. Sachima may record them as observations; it must never feed them back into request construction, and must never treat them as the effective configuration of a Run other than the one that produced them (§5.5.4).

Sachima treats a non-null `quarantine` as: **this Session is not reusable**. The task's continuity is broken and requires an explicit Sachima-side decision (start a new Session under a new dispatch, or surface a stable blocked status). Sachima must not auto-heal, auto-recreate, or retry into a quarantined Session.

### 6.5 Run terminal vocabulary

The Native ACP terminal vocabulary is exactly five members:

```text
completed  failed  cancelled  timed_out  unknown
```

Terminal evidence has exactly three trust kinds: **ABSENT**, **TRUSTED**, **INVALID**. Only TRUSTED evidence may move Sachima's canonical status. INVALID terminal evidence causes the daemon to contain the Run, quarantine the bound Session, and refuse with `INTERNAL` — Sachima maps that to a stable internal/contained failure and never fabricates an outcome (§10.5).

## 7. Identity, idempotency, and private Run+Session binding

### 7.1 Request identity

`request_id` is derived from the admitted Sachima dispatch identity only:

```text
(task_id, session_id, dispatch_ref) -> sachima-<sha256 hex>
```

Never from wall-clock time, never from a counter. A retry of an uncertain submission reuses the exact same `request_id` **and** a byte-equivalent payload (proven by `arsd_submit_payload_digest`, without persisting the payload). Both facts are read back from the **pending submission intent** written before that submit (§7.3.1); that record is what makes byte-equivalence *provable* after a lost ack rather than merely asserted. The daemon keys idempotency on `(principal_id, request_id)`; the same id with different material returns `IDEMPOTENCY_CONFLICT`.

On `IDEMPOTENCY_CONFLICT`, Sachima **fails closed** with a stable conflict code. It must not mint a new id and resubmit.

### 7.2 Submit ack

The ack is exactly:

```text
{run_id, session_id, accepted_at}
```

A duplicate submit under the same `request_id` returns the same three facts, read back from the durable submission, and dispatches nothing a second time.

### 7.3 Private binding ledger

A dispatch has exactly **one** logical durable record, in one of two states: a **pending submission intent**, written before the first socket submit (§7.3.1), and the **accepted binding** that same record becomes when a validated ack finalizes it in place. There is never a second record for a dispatch, and an accepted binding never appears without a pending intent having preceded it.

On a successful ack, Sachima privately binds:

```text
(task_id, dispatch_ref) -> (run_id, session_id, accepted_at, request_id, payload_digest)
```

Rules:

1. **Both** `run_id` and `session_id` are private locators. Neither is public status text, neither is serialized into `TaskEventLog`, projections, view models, logs, or user-visible surfaces. Public surfaces carry only Sachima-derived safe refs (`run_ref`, `source_ref`).
2. The binding is what makes restart-safe resumption possible: after a Sachima restart, observation resumes from the recorded `run_id` — there is no re-dispatch.
3. `session_id` is recorded on the **first** turn and reused verbatim on later turns of the same task.
4. `retry_of_run_id` is populated only by an explicit operator/recovery decision, never as an automatic response to a timeout or a disconnect.
5. The accepted binding is always the **finalization of a pending intent**, never a newly created record. Sachima never writes an accepted binding for a dispatch that has no pending intent, and never writes a second record for a dispatch that has one.

#### 7.3.1 Pending submission intent — the record that survives a lost ack

A binding created only after the ack cannot survive the loss of that ack: if the reply never arrives, Sachima holds no durable proof of which `request_id` and which payload were in flight, and §7.1's "reuse the exact same `request_id` with a byte-equivalent payload" becomes unimplementable. The record is therefore written **before** the submit, in the same private ledger seam, and finalized after it.

**Write.** Before the **first socket submit** of a new admission — after the current-budget pre-check has passed (§5.6.2) and before any bytes reach the socket — Sachima atomically persists a pending submission intent. The submit is not attempted until that write has durably landed.

**Contents.** Exactly what a later reconstruction needs, and nothing more:

```text
deterministic dispatch identity   # the same components request_id is derived from (§7.1)
request_id                        # the exact id that will be sent
payload_digest                    # arsd_submit_payload_digest of the frozen payload
resolver_refs                     # the minimum private/non-secret immutable refs the
                                  #   builder consumed: policy refs, workspace ref,
                                  #   grant ref/hashes, and the resolved-config refs
```

**What it must never contain.** Raw prompt or payload text, credential values, socket paths, daemon run/session directories, remote text of any kind, or the payload itself — §7.1's "without persisting the payload" is unchanged. The intent holds refs and digests only, and its private fields obey §9.5's no-leak discipline exactly as the accepted binding's do: nothing in either state is public status text, serialized into `TaskEventLog`, projected, or logged.

**Finalize.** On a **validated** ack, Sachima finalizes that same intent **in place** — atomically adding `run_id`, `ars_session_id`, and `accepted_at` and marking it accepted. A finalize against a missing intent, or against one already accepted with different material, fails closed with the stable binding-conflict code. No second logical record is ever created.

**Lost or indeterminate submit.** The pending intent is left exactly as written, **fail-closed** (§10.3). It is not deleted, not finalized by inference, not treated as evidence of acceptance, and not replayed. Nothing — not a timeout, a disconnect, a restart, or a reconciliation pass — may act on it automatically. The dispatch stays blocked until an explicit decision resolves it.

**Recovery.** A **separately invoked, explicit** recovery entry point:

1. reads the pending intent;
2. reconstructs the payload through the **same resolver**, from the recorded `resolver_refs`, and requires the reconstruction to be **byte-equivalent** with a digest equal to the recorded `payload_digest`;
3. on a **mismatch**, fails closed with the stable binding-conflict code **before any socket I/O** — zero socket calls. Sachima can no longer prove byte-equivalence, so it must not submit at all rather than send material it cannot vouch for and earn `IDEMPOTENCY_CONFLICT` (§7.1);
4. on a match, submits the **same `request_id`** with that byte-equivalent payload, performing no new-admission negotiation and no current-budget pre-check (§5.3.1 consequence 3);
5. finalizes that same pending intent **exactly once** on the resulting durable ack.

Never a fresh `request_id`, never an automatic `retry_of_run_id`, never a replay Sachima started by itself. These are acceptance rows A-7 and A-8.

### 7.4 Concurrency

The daemon refuses a concurrent Run on a busy Session with `SESSION_BUSY`, including for a create Run tracked under its prospective Session id. Sachima additionally enforces **at most one active Run per task/session binding** on its own side; the dispatcher single-flight window covers submit/admission only, and must not be mistaken for a lock held for the duration of the Run.

## 8. Transport-neutral Runtime Spine interface implications

### 8.1 The neutral backend contract

The turn dispatcher and the execution binding currently require the concrete `AgentRunSupervisorLibraryBackend` type. Both concrete-type couplings must be replaced by one Sachima-owned validated contract:

```text
create_or_attach(task_id, refs) -> handle
attach_existing(task_id)        -> handle
run_turn(task_id, *, turn_kind, payload_text, dispatch_ref) -> SupervisorTurnResult
status(handle)   -> str
signal(handle, decision_ref) -> str
kill(handle, reason_ref)     -> str
liveness(handle) -> str
```

Backend construction goes through an explicit factory allowlist for `fake` and `arsd`. Arbitrary duck-typed objects are not accepted at a production composition root.

### 8.2 `SupervisorTurnResult` must lose `turn_dir`

The current result carries `turn_dir` — a library-private filesystem path. Daemon-private storage layout is **not caller contract** under this integration: `arsd` owns `native-runs/<run_id>` and Sachima must not read it, name it, or model it.

The neutral result carries safe references and observations only:

```text
run_ref          # Sachima-derived safe ref (never the raw run_id)
source_kind      # "arsd_run" | "artifact_file" (fake/offline)
source_ref       # safe ref for the read-model source
supervisor_status
foreign_cursor   # foreign read-model position; never TaskEventLog.seq
```

Every existing `turn_dir` consumer must be re-expressed against this neutral shape or dropped. Known consumers at this baseline: the library backend result type, the turn dispatcher's outcome construction, and the real-execution activity's artifact-count observation.

### 8.3 Transport-neutral status vocabulary

```text
accepted | completed | failed | cancelled | timed_out | unknown
```

`run_turn` for `arsd` is a **submit**: it returns after durable acceptance with `supervisor_status="accepted"`. It does not block until the external AGENT terminates. Terminal truth arrives later through `run_status` observation (§10).

### 8.4 Source bindings

`LiveProgressSourceBindings` currently assumes a private `artifact_dir`. It is extended additively with tagged private locators:

```text
artifact_file : private artifact_dir
arsd_run      : private run_id
```

The serializable/public projection stays refs-only: `source_kind`, `artifact_ref`/`run_ref`, `last_seen_cursor`. Neither `artifact_dir`, `run_id`, nor `socket_path` is ever serialized.

## 9. Events, cursors, projection, and no-leak

### 9.1 Read events through the socket only

Sachima reads run evidence exclusively via:

```text
run_events(run_id, from_seq=<cursor>, limit=<page_size>, follow=False)
```

Bounded pagination only. No resident `follow` subscription in the first implementation. No direct read of daemon run directories, ever.

### 9.2 Cursor translation

```text
next_from_seq -> resume_cursor
exhausted     -> has_more = not exhausted
```

`from_seq` and Sachima's `after_seq` are both **exclusive** last-seen cursors. `next_from_seq` is the highest sequence returned on the page, so resuming from it neither duplicates nor drops records. On an empty page it equals the request cursor.

A byte-budget truncation marker page carries exactly one synthetic marker event and reports `exhausted: false`. Validators and fixtures must preserve that exact shape.

### 9.3 The cursor is foreign — hard rule

The ARS event sequence is a **foreign read-model cursor**. It lives in the source-binding/read-model layer and is **never** appended as, mapped to, offset into, or reconciled with `TaskEventLog.seq`. Sachima's monotonic sequence authority is Sachima's alone.

### 9.4 Projection allowlist

Only closed structural data crosses into the workbench/projection:

- stable event family/type;
- event count;
- safe status;
- normalized, already-approved text length/count metadata;
- cursor and exhaustion flags;
- Sachima-derived safe refs.

Discarded without exception: raw text, message bodies, final messages, tool payloads, stderr, exception text, child/daemon paths, credentials, agent-authored text, remote error messages.

### 9.5 No-leak invariants

| Value | Rule |
|---|---|
| `socket_path` | private field, `repr=False`, no serialize surface, never logged |
| `prompt_text`, payload text | caller-owned wire material; goes to the facade `submit` and nowhere else |
| `run_id`, `session_id` | private locators; only derived safe refs are public |
| daemon run/session directories | never named, never read, never modeled |
| remote `error.message` | discarded at the client boundary; Sachima never re-reads it |
| workspace/cwd paths | private absolute paths outside the tracked repo; never serialized |

Every failure raises a Sachima `SpineError` whose message **is** the stable code.

### 9.6 ARS-internal evidence behavior (0.7.3) — no Sachima surface

Two ARS-internal changes landed in 0.7.3 (Δ-4, Δ-5). Neither is a Sachima protocol surface, and neither requires code:

- Session-load replay events are isolated from the current Run and represented by a bounded summary. Sachima reads the *current* Run's evidence through `run_events(run_id, ...)`, so a reuse turn's pages are that Run's, not a replay of earlier turns.
- Per-Run evidence uses a bounded serial ledger and a backpressure policy. When backpressure bites, it surfaces as the existing `EVENT_BACKLOG_EXCEEDED` wire code, already mapped to `runtime_arsd_busy` (§13.2) — a transient category, never a Run failure and never a canonical mutation.

The wire, API, and schema shapes, Session lifecycle, terminal vocabulary, and per-event truncation semantics are all unchanged, so §9.1–§9.5 stand exactly as accepted. Sachima must not build a new dependency on the replay-isolation behavior beyond what §4.3 already pins: the page shape is the contract; the internal ledger is not.

## 10. Liveness, disconnect, cancellation, terminal truth, and quarantine

### 10.1 Status observation

`run_status` returns either an acceptance view (`{run_id, session_id, state: "accepted", accepted_at}`) or a body carrying optional `progress` and/or a trusted `result`.

| ARS observation | Sachima state |
|---|---|
| `accepted` / progress present, no terminal | `running` |
| trusted terminal `completed` | `completed` |
| trusted terminal `failed` | `failed` |
| trusted terminal `cancelled` | `cancelled` |
| trusted terminal `timed_out` | `failed` |
| trusted terminal `unknown` | `ambiguous` |
| observation unavailable (disconnect, unreadable, daemon down) | **backend read failure — canonical state is not mutated** |
| invalid/untrusted terminal evidence | contained backend failure; never a fabricated success |

### 10.2 Disconnect is observation loss

A socket disconnect, a daemon restart, or a failed read means Sachima *did not observe*. It does not mean the Run failed.

Required behavior: retain the last canonical projection, mark the observation attempt as failed with a stable transient code, and retry observation with a **fresh** client on the next explicit query or reconciliation. Never mark, kill, mutate, or re-dispatch on observation loss.

### 10.3 Indeterminate submission

A local transport loss *during a submit*, before a complete reply is read, is **indeterminate**: the daemon may already hold the Run. That outcome maps to `runtime_arsd_submission_indeterminate` and is surfaced for an explicit recovery decision.

A **lost ack is the same case**, and it is the case that makes the pending submission intent load-bearing: the daemon may have accepted and recorded the submission, and Sachima may still never read the reply. The intent written before that submit (§7.3.1) is the only Sachima-side record proving which `request_id` and which `payload_digest` were in flight. It survives the loss untouched and fail-closed, and it is what a later recovery reads.

There is **no automatic uncertain replay**. Recovery is the explicit entry point of §7.3.1: reconstruct the frozen payload from the intent's `resolver_refs` through the same resolver, refuse with zero socket calls if the rebuilt digest differs from the recorded one, and otherwise re-issue the *identical* `request_id` with the byte-equivalent payload (which the daemon resolves idempotently against its durable admission record), finalizing that same intent exactly once. Or make an explicit operator decision. Never a fresh `request_id`, never an automatic `retry_of_run_id`, never a replay Sachima started by itself.

### 10.4 Cancellation

`ExecutionPort.kill()` maps to exactly one operation: `run_cancel(active_run_id)`.

- It **never** closes a Session. There is no close.
- `run_cancel` returns `{run_id}`, plus `result`/`status` when trusted terminal evidence exists.
- Sachima projects `cancelled` only on trusted terminal evidence. If the outcome is not yet trusted, Sachima waits/re-queries `run_status` within its own bounded policy and otherwise reports `ambiguous` or a backend-observation failure. It never claims a successful cancel it cannot prove.
- Closing a follow connection or a client connection never cancels a Run.

### 10.5 Quarantine

Quarantine is continuity evidence, produced by the daemon when a Run's terminal evidence is untrusted or a dispatch cannot be proven. Sachima's obligations:

1. Read it only as the closed categorical structure from `session_status`/`session_list`.
2. Treat a quarantined Session as **not reusable**; a reuse attempt is refused pre-dispatch by the daemon with a stable detail code and no child, no prompt, no fallback Session.
3. Never project quarantine evidence as user-visible text; map it to a Sachima-owned stable blocked/ambiguous state.
4. Never attempt to clear, un-quarantine, or work around it. That is operator territory.

### 10.6 Permission decisions

Socket API v3 has no external `signal(decision_ref)` operation. ARS mediates ACP permission requests from the frozen grant supplied at submit time.

Therefore the first `arsd` backend:

- admits only roles whose permissions are fully determined **before** submit;
- keeps `ExecutionPort.signal()` fail-closed in `arsd` mode;
- does not invent a `permission_wait → running` transition;
- requires a separate ARS protocol capability before any operator-in-the-loop permission decision is possible.

Grant capabilities remain restricted to the read-only allowlist (`read`, `search`); write-capable grants stay fail-closed.

#### 10.6.1 Profile and ACP-mode derivation (0.7.4)

ARS derives the Codex ACP mode from **each Run's frozen grant**, and exactly reads it back; the policy never selects `agent-full-access` (Δ-7). 0.7.4 also added OMP and Reasonix as profile sources (Δ-6).

These are profile semantics, not Socket API shape changes, and they narrow rather than widen what Sachima does:

- Sachima supplies a **frozen grant**, never an ACP permission mode. There is no mode field for Sachima to set and none for it to model.
- Because the mode is derived from the grant, Sachima's read/search-only grant cannot yield `agent-full-access`. Sachima must not model, request, or plan for one.
- Profile sources (including OMP and Reasonix) are operator/registry territory under §12.4. Sachima's config gains **no** profile-source selection; `agent_by_policy_ref` remains its only agent-facing choice.

#### 10.6.2 `read` / `search` path resolution (0.7.6)

At 0.7.6, a `read`/`search` allow requires **both** the frozen `read` grant **and** that every declared path resolves, through symlinks, inside the bound workspace. If any declared path fails to resolve inside it, the call is denied fail-closed (Δ-13).

The declared paths are the agent's tool-call arguments, mediated by ARS at request time. Sachima neither predicts nor overrides that verdict. Sachima's only two levers are:

1. the frozen grant it supplies at submit — which must carry `read` for any read/search work to be allowed at all; and
2. the `workspace_root` and `cwd` it declares at submit.

**`cwd` must resolve inside `workspace_root`.** A `cwd` outside the bound workspace makes every subsequent read/search deny fail-closed, turning a correctly configured Run into a guaranteed failure. This is an offline-checkable submit-builder obligation (acceptance row A-28): a submit whose `cwd` does not resolve inside `workspace_root` fails closed Sachima-side before any socket call. Whether a *specific* agent tool-call path resolves inside the daemon's bound workspace is an ARS-side runtime verdict, proven only at the canary gate.

#### 10.6.3 Write capabilities exist at 0.7.6 — and stay closed here

`edit`, `delete`, and `move` requests can receive a once-scoped allow when the matching frozen grant capability exists (Δ-14). This is recorded because it is true, **not because Sachima adopts it.**

Sachima's first integration is intentionally limited to `read`/`search`. `grant_capabilities` stays exactly `{read, search}`; a config declaring `edit`, `delete`, or `move` fails closed (acceptance row A-27). Opening a write-capable grant is a separate approval that this Spec does not grant, does not prepare, and does not plan for.

#### 10.6.4 Cooperative mediation is not isolation

ARS's permission mediation is **cooperative**: it is a policy boundary a well-behaved agent respects, not an OS-level sandbox (Δ-16).

Two consequences, both about accuracy rather than new hardening:

- Sachima's documents, codes, and status text must not describe ARS permission mediation as isolation, containment, or a sandbox.
- Grant scope must not be widened on the assumption that ARS bounds the blast radius. The read/search-only first cut is the actual boundary, and it stays that way.

### 10.7 Permission-violation terminal (0.7.6)

A tool call that was denied and is later reported completed produces a terminal `PERMISSION_VIOLATION` outcome. It is **non-retryable**, and the Session **remains reusable** (Δ-15).

This does not add a sixth member to the five-member Run terminal status vocabulary (§6.5), which is unchanged. It is a terminal *reason*, and Sachima handles it through the paths it already has:

| Aspect | Sachima obligation |
|---|---|
| Trust | It is **trusted terminal evidence of a failure**, not observation loss and not untrusted evidence. Canonical status moves through the ordinary trusted-terminal path (§10.1), not the contained-internal path (§10.5) |
| Retry | Non-retryable means **no** automatic retry, **no** new `request_id`, and **no** `retry_of_run_id`. Recovery, if any, is an explicit operator decision (§10.3) |
| Session | The Session is **not** quarantined by this outcome and stays reusable. Sachima must not start a second Session, must not mark the binding broken, and must not re-create continuity it did not lose |
| Surface | The reason is categorical evidence. It never becomes user-visible text; it maps to a Sachima-owned stable failure category (§13) |

The distinction that matters: a `PERMISSION_VIOLATION` terminal means *this Run is over and failed for a policy reason*, not *this conversation is broken*. Treating it as the latter would discard a healthy Session and re-dispatch work ARS already refused. This is acceptance row A-26.

## 11. Legacy library / acpx retirement and explicit migration behavior

### 11.1 The fact

`agent-run-supervisor` 0.7.x removed the legacy library surface and the legacy `acpx` product. The modules Sachima's `library` mode imports lazily — `role`, `workspace`, `session_runtime`, `session_inspect`, `goal`, `caller`, `hermes_caller.events` — **do not exist** in 0.7.1 and are still absent at 0.7.6. The `library` backend is therefore not degraded; it is unrunnable.

### 11.2 Required behavior — fail closed with a migration error

Selecting `library` (via config or `SACHIMA_LIVE_PROGRESS_BACKEND=library`) must:

1. **Fail closed** with one stable Sachima-owned migration code — a *distinct* code, not reused `runtime_arsd_unavailable` and not a generic invalid-config code, so the operator can tell "you selected a retired mode" from "the daemon is down".
2. Emit a stable, non-echoing message that names the supported choices: **`fake`** or **`arsd`**.
3. Leave the tool/service unbound, dispatch nothing, launch nothing, and mutate nothing.

### 11.3 Forbidden migration behaviors

- **No silent rewrite.** `library` must never be silently coerced to `fake` or `arsd`. A silent rewrite would run a different backend than the operator asked for.
- **No fallback.** No fallback to direct CLI, to the library, to `acpx`, or to `npx`.
- **No degraded emulation.** No attempt to reimplement `session_runtime`/`session_inspect` behavior against daemon-private storage.

### 11.4 Scope of retirement in Sachima

The retirement touches every place that reaches the removed modules: the library backend facade, the real-execution activity's default backend, the local-offline caller path, and the live-progress projection's caller-events reader. Each becomes either (a) re-pointed at the socket path, (b) fake/offline-only, or (c) explicitly retired with the stable migration error. Whether a given seam is (a), (b), or (c) is an implementation-plan decision; that every one of them stops depending on removed modules is a Spec requirement.

`fake` remains the default offline/dev mode and must stay fully functional with no `agent_run_supervisor` import at all.

## 12. Package, config, and daemon ownership

### 12.1 Package

`agent-run-supervisor` is consumed **only** as the installed exact-pinned distribution: `pyproject.toml` extra + mirrored `dev`, `EXPECTED_AGENT_RUN_SUPERVISOR_VERSION`, regenerated `uv.lock`, and a narrowed `[tool.uv].exclude-newer-package` entry. Zero source-path references — no `sys.path` shim, no sibling-checkout constant, no `PYTHONPATH` instruction — remains a guarded invariant.

Importing any Sachima module must never import `agent_run_supervisor` at module load. Only facade operations import it, lazily, inside the call.

### 12.2 Config

`ArsdSupervisorConfig` stays a frozen, default-off, host-owned config carrying private paths and closed policy-ref maps:

```text
type  enabled(default False)  approval_ref  socket_path(private)
expected_package_version = 0.7.6
required_api_version     = 3
owner  namespace
agent_by_policy_ref  model_by_policy_ref  effort_by_policy_ref
workspace_by_ref  run_limits_by_policy_ref
grant_ref  grant_hash  grant_role_hash  grant_capabilities
mcp_snapshot_hashes  credential_refs  evidence_policy_hash  recovery_policy_hash
```

Construction fails closed unless `enabled is True` (exactly the bool), the config type is exact, paths/refs are valid, private paths sit outside the tracked repo, and every map is an owned immutable copy. No raw credential value ever belongs here.

The field set does **not** grow for 0.7.6. Three existing maps carry the calibrated obligations:

| Map | Obligation |
|---|---|
| `model_by_policy_ref`, `effort_by_policy_ref` | The only source of each Run's `requested_model` / `requested_effort` (§5.5). Scope is exactly these two values; no other ARS configuration is injected per Run |
| `run_limits_by_policy_ref` | Values are validated against the mirrored `LIMIT_*` maxima **and** against the admission product `max_event_bytes * max_events <= max_run_event_budget_bytes` using the currently negotiated budget (§5.6.2) |
| `grant_capabilities` | Stays exactly `{read, search}`; `edit`/`delete`/`move` fail closed (§10.6.3) |

No profile-source, ACP-mode, or event-budget field is added to Sachima's config: profile sources and the daemon's configured budget are operator-owned (§12.4), and the budget is read from `server_info`, never declared by Sachima.

### 12.3 Gateway composition

```text
SACHIMA_LIVE_PROGRESS_BACKEND = fake | arsd     ("library" -> stable migration error, §11)
```

- unset/blank remains `fake`;
- `arsd` requires the existing exact `hermes_internal` surface gate **and** an explicit private config file;
- a malformed or disabled config leaves the tool unbound and returns one stable code;
- composing the display service must never submit a Run;
- dispatch requires a separately injected payload resolver/admission path;
- no automatic fallback to any other backend.

### 12.4 Daemon ownership — operator, not Sachima

Sachima and Gateway do **not** own any of the following. The operator does:

| Concern | Owner |
|---|---|
| Installing/activating the `agent-run-supervisor` package that runs the daemon | Operator |
| Starting, stopping, restarting `arsd`; the systemd user unit | Operator |
| The agents registry file (read exactly once at daemon startup) | Operator |
| Profile sources and profile configuration, including the 0.7.4 OMP / Reasonix sources | Operator |
| The daemon's configured `max_run_event_budget_bytes` (Sachima reads the negotiated value; it never declares one) | Operator |
| Socket path, socket/dir permissions, peer→principal caller mappings | Operator |
| Supervisor root and daemon-private storage | Operator |
| Deploys, upgrades, and post-restart reconciliation | Operator |

Sachima is a caller. It connects to a socket that already exists; it never starts, restarts, provisions, or repairs the daemon, and it never writes daemon configuration. A registry or agent change costs an operator-owned daemon restart — Sachima must be correct across that restart, not attempt to trigger it.

## 13. Failure mapping — stable Sachima-owned categories

### 13.1 Principle

Sachima emits **only** its own stable codes. Remote `message` text is discarded at the client boundary and never re-read, re-raised, chained, stored, logged, or shown. The Sachima error's message **is** the code.

### 13.2 Mapping

| Wire code | Sachima stable code |
|---|---|
| `UNSUPPORTED_API_VERSION` | `runtime_arsd_version_mismatch` |
| `UNKNOWN_OP`, `MALFORMED_FRAME`, `FRAME_TOO_LARGE` | `runtime_arsd_protocol_violation` |
| `INVALID_REQUEST` | `runtime_arsd_invalid_request` |
| `UNAUTHENTICATED_PEER`, `PEER_UID_DENIED`, `OWNER_MISMATCH` | `runtime_arsd_policy_denied` |
| `IDEMPOTENCY_CONFLICT` | `runtime_arsd_idempotency_conflict` |
| `SUBMISSION_INDETERMINATE` | `runtime_arsd_submission_indeterminate` |
| `UNKNOWN_RUN`, `UNKNOWN_SESSION` | `runtime_arsd_unknown_target` |
| `SESSION_BUSY`, `CAPACITY_EXHAUSTED`, `EVENT_BACKLOG_EXCEEDED` | `runtime_arsd_busy` |
| `SHUTTING_DOWN` | `runtime_arsd_shutting_down` |
| `INTERNAL` | `runtime_arsd_internal` |
| client-local `CLIENT` | `runtime_arsd_unavailable` |
| unknown / wrong-type / casing-drifted code | `runtime_arsd_internal` (fail closed) |

Sachima-side codes not derived from the wire: `runtime_arsd_disabled`, `runtime_invalid_arsd_config`, and the new §11 migration code.

### 13.3 Operation-aware refinements

| Situation | Stable code | Why |
|---|---|---|
| Connect-phase failure | `runtime_arsd_unavailable` | Nothing was sent |
| Base-class client error with `INVALID_REQUEST` during a roundtrip | `runtime_arsd_protocol_violation` | Response-correlation failure (off-contract reply), not a daemon verdict on our request |
| Base-class transport loss (`INTERNAL`/`MALFORMED_FRAME`) **during a submit** | `runtime_arsd_submission_indeterminate` | The frame may have reached the daemon with its verdict unread |
| Same transport loss during a non-submit read | `runtime_arsd_unavailable` | Observation loss only (§10.2) |
| Close failure with no other active error | `runtime_arsd_unavailable` | Local hygiene failure |

### 13.4 Business-status boundary

None of these codes is user-visible text. They are Sachima-internal categories. The user-visible business status is produced by Sachima's Status Projection from Sachima-owned state, and stays inside the product vocabulary.

## 15. Non-goals and explicit non-approvals

### 15.1 Non-goals

- No compatibility shim for API v2, for the v2 request shape, or for old Session-close semantics. There is no external caller population to drain, and this environment has **no obligation** to preserve old locally persisted ARS state.
- No `session_close` emulation, no Session lifecycle projection, no "closed" state.
- No resident `follow` subscription in the first implementation.
- No operator-in-the-loop permission mediation over the socket.
- No reading, mirroring, or modeling of daemon-private storage layout.
- No dual-backend runtime that can fall back between `library` and `arsd`.
- No expansion of security scope, phases, or deployment prerequisites beyond what the usable integration needs.
- No adoption of the 0.7.6 once-scoped `edit`/`delete`/`move` allow path. It is recorded (§10.6.3), not used.
- No profile-source selection (OMP, Reasonix, or any other) in Sachima config; no ACP-mode selection of any kind.
- No general per-Run configuration-injection channel. The override scope is exactly `requested_model` and `requested_effort` (§5.5.1).
- No Sachima-side re-implementation of ARS admission policy beyond the one arithmetic pre-check in §5.6.2, and no Sachima-invented timeout, budget, or limit constant.

### 15.2 Non-approvals (standing, unchanged)

This Spec approves none of: source/test/dependency/lock changes; the implementation plan; commit/push/PR/merge; Git branch/worktree operations; network or GitHub access; package installation; daemon start, socket connection, `server_info`, or `submit`; real AGENT/ACP execution; Gateway, Feishu, Temporal, Worker, service, config, restart, or deploy actions; write-capable roles; real delivery; production traffic; turning `arsd` on; or Sachima D2+ implementation.

`docs/roadmap/boundary-register.md` non-approvals remain in force in full.
